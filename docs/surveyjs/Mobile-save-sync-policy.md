# Mobile SurveyJS Save, Sync, and Triggered Action Policy

This document defines how the Expo mobile app saves SurveyJS questionnaire data, promotes finalized local evidence, syncs to backend, and handles triggered downstream actions.

## Scope

This policy applies to SurveyJS forms in the Expo app, with HHQ as the first required implementation target.

Primary implementation areas:

- `expo-prototype/src/modules/questionnaires/QuestionnaireDashboard.js`
- `expo-prototype/src/modules/questionnaires/questionnaireDraftRepository.js`
- `expo-prototype/src/modules/questionnaires/questionnaireSubmissionRepository.js`
- `expo-prototype/src/modules/tasks/taskRepository.js`
- `expo-prototype/src/modules/sync/syncService.js`
- `apps/api/src/routes/sync.ts`
- `apps/api/src/services/eventProcessor.ts`

## Core Rule

Drafts are local recovery state. Finalized form responses are immutable evidence.

Only finalized form responses can promote operational state, create or update households and members, generate next-form opportunities, generate tasks, or sync to backend.

## Draft Save Policy

Autosave and `Save Draft` are local-only.

Draft save writes SurveyJS `model.data` to local app storage through `questionnaireDraftRepository.js`.

Drafts:

- are keyed by form, form version, task, subject, device, and user
- can be overwritten by later draft saves for the same draft key
- are not uploaded to backend
- do not create or update households
- do not create or update household members
- do not generate downstream tasks or next-form actions
- do not win any conflict against finalized evidence

Opening Preview first saves the current SurveyJS data as a draft, but the data remains draft state until final confirmation succeeds.

## Final Save Policy

Final confirmation creates one canonical local form response.

For HHQ, final confirmation must:

1. Save an immutable local `form_response` with `sync_status = pending`.
2. Include top-level scope fields needed by sync and backend promotion:
   - `household_id`
   - `site_id`
   - `locality_code`
   - `form_code`
   - `form_version`
   - `answers_json`
   - `submitted_at`
   - `device_id`
3. Create or update the local household row if it does not already exist.
4. Create, replace, or upsert local household member rows from the HHQ roster.
5. Store provenance on promoted local rows:
   - `source_form_response_id`
   - `source_form_code`
   - `source_submitted_at`
   - `source_sync_status`
6. Mark the active draft as submitted.
7. Trigger local downstream actions that are valid from finalized HHQ evidence.

The generic `/questionnaires/HHQ/new` route and any task-opened HHQ route must use the same finalization path. A finalized HHQ must not remain only in `dynamic_questionnaire_submissions_v1`.

## HHQ Local Promotion Policy

HHQ final confirmation is allowed to create the local household if the computed `household_id` does not already exist.

The local app must use the HHQ final response to immediately support the next valid offline workflows. The field user must not have to wait for backend sync before opening valid downstream forms that depend on the HHQ roster and eligibility state.

HHQ local promotion should derive:

- household identity from `hhq_site_id`, `hhq_locality_code`, `hhq_structure_map_id`, and `hhq_household_number`
- household registry fields from HHQ answers
- household members from `hhq_household_members`
- woman questionnaire eligibility from member sex, age, and marital status rules
- next valid local actions from shared workflow rules

The old household registry extraction path can be reused, but it must become part of the canonical HHQ finalization path instead of remaining a separate non-syncing save path.

## Triggered Actions Policy

Triggered actions run only after final confirmation, never on draft save.

After finalized HHQ local promotion, Expo should expose or generate only protocol-valid next actions, including:

- WQ opportunities for eligible women derived from the finalized HHQ roster
- HRF scheduling context anchored to the HHQ baseline completion date
- any other local task or opportunity generated by shared workflow rules

Forms must still open only from scheduled tasks or valid contextual trigger buttons. Do not add a global open-any-form workflow.

Triggered local actions must carry provenance back to the form response that created them.

## Sync Push Policy

Sync pushes immutable evidence, not separately edited local household tables.

`pushSync()` must include pending finalized `form_response` rows and domain events.

For HHQ, the pushed record must include enough top-level scope for `/sync/push`:

```text
type = form_response
data.id = local form_response id
data.form_code = HHQ
data.form_version = HHQ version
data.household_id = computed household_id
data.site_id = numeric site_id
data.locality_code = locality_code
data.subject_type = household
data.subject_id = household_id
data.answers_json = SurveyJS finalized payload
data.submitted_at = finalized instant
```

Local `households`, `household_members`, and older `form_submissions` tables are not the canonical push payload for HHQ. They are local promoted operational state derived from the immutable form response.

## Backend Promotion Policy

Backend `/sync/push` stores the immutable form response first, then promotes it.

For HHQ, backend promotion must:

1. Derive `household_id`, `site_id`, `locality_code`, structure number, and household number from the top-level sync record and/or HHQ answers.
2. Create the household row if it does not exist.
3. Update baseline household fields if the household already exists.
4. Upsert household members from the HHQ roster.
5. Generate canonical HRF tasks and other downstream state through shared workflow rules.
6. Record promotion provenance from the source form response.

HHQ backend promotion must not reject a valid finalized HHQ only because the household row is missing. HHQ is allowed to create the household.

## Pull Merge Policy

The merge rule is latest finalized evidence wins.

Drafts never win. Pull rows must not overwrite newer local state derived from a finalized local form response.

Each promoted household, member, task, or opportunity row should carry the source finalized evidence that produced it:

```text
source_form_response_id
source_form_code
source_submitted_at
source_sync_status
promoted_at
```

Merge decisions must compare evidence provenance, not raw storage update time alone.

Rules:

- If local state is derived from a pending finalized response that is newer than pulled backend state, keep local state.
- If backend confirms the same `source_form_response_id`, mark the local promoted rows accepted or synced.
- If backend has a newer accepted finalized response or correction evidence, backend state can replace local promoted state.
- If local has newer unsynced finalized evidence, local state remains active for offline routing and next forms.

## Time and Timezone Policy

Do not use a single timestamp for all decisions.

### Event Dates

Protocol and interview dates, such as `hhq_interview_date`, are calendar dates.

Store them as `YYYY-MM-DD` and interpret them in the study or site timezone. Do not convert these dates to UTC instants.

### Device Finalized Time

When Expo finalizes a form locally, store:

```text
device_submitted_at_utc
device_timezone
device_timezone_offset_minutes
device_sequence
device_id
```

Before sync, local ordering on the same device should use `device_sequence` as the primary provisional order. Device wall-clock time is audit information and a fallback, not the only ordering source.

### Server Accepted Time

When backend accepts a finalized response, store:

```text
server_received_at_utc
server_commit_sequence
```

After sync, cross-device ordering should use backend acceptance order, with `server_commit_sequence` as the primary order key.

### Same Response Confirmation

When backend confirms the same `form_response_id` that was already promoted locally, the app must mark the local state accepted or synced. It must not treat the backend copy as a competing newer update.

## Implementation Target

The locked target data path is:

```text
HHQ final confirm in Expo
 -> save pending immutable local form_response
 -> promote local household and household_members
 -> generate local next-form actions from shared workflow rules
 -> sync pushes form_response
 -> backend stores immutable form_response
 -> backend creates or updates household and household_members
 -> backend generates canonical tasks
 -> pull merge applies latest finalized evidence wins
```
